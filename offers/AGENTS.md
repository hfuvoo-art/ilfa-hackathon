# offers/ — ML/LLM-разработчик. План для ИИ-ассистента

Ты помогаешь **ML/LLM-разработчику**. Твоя зона — только папка `offers/`. Перед работой прочитай корневой `AGENTS.md` и `shared/DATA_CONTRACT.md`.

## Цель
Для каждого пациента определить **повод** связаться, **предложение**, **тон** и **текст**, который звучит как забота, а не реклама. Примеры из кейса: пациенту с имплантом — напоминание о гигиене через год; тому, кто делал только гигиену — мягкое предложение проверить кариес; молодой маме — акцент на безболезненность; пожилому — на надёжность и гарантии.

## Вход
- Таблицы `patients`, `visits`, `visit_items`, `services` (от `etl/`).
- `patients.segment` и матрица переходов между категориями (от `analytics/`).
- Комментарии администраторов (`visits.comment`, заполнены в 86% визитов).
- **В данных нет возраста и телефона.** Персону выводи косвенно: детские услуги, комментарии, тип лечения.

## Выход (в `offers/`)
1. `offers/triggers.yaml` — каталог триггеров (повод, условие, предложение, срок, базовый приоритет).
2. `offers/rules.py` — `find_triggers(patient, visits, items) -> list[Trigger]`.
3. `offers/tags.py` — признаки из комментариев → таблица `comment_tags`.
4. `offers/templates.py` — шаблонные тексты: триггер × тон (работают БЕЗ интернета и LLM).
5. `offers/llm.py` — генерация текста через LLM (ключ из `.env`), с кэшем.
6. `offers/build.py` — точка входа: `python -m offers.build [--llm]` заполняет таблицу `offers` для всех пациентов.
7. `offers/EXAMPLES.md` — 10–15 примеров «история → повод → тон → текст» для презентации.
8. `offers/requirements.txt`, `offers/.env.example`.

## Шаги

### Шаг 1. Триггеры на правилах (часы 2–10)
Коды триггеров — строго из контракта:
| trigger | Условие (стартовое) | Предложение | tone по умолчанию |
|---|---|---|---|
| `implant_control` | была установка импланта или коронка на имплант, прошло ≥ 330 дней | контрольный осмотр + гигиена | `reliability` |
| `hygiene_due` | последняя гигиена ≥ 180 дней назад | профгигиена | `care` |
| `hygiene_only` | все платные услуги — гигиена | мягко: диагностика кариеса | `light` |
| `unfinished_implant` | КТ/консультация имплантации или установка без следующего этапа | продолжить лечение, гарантии | `reliability` |
| `unfinished_ortho` | брекеты/элайнеры, нет ортодонтического визита > 60 дней | вернуться на коррекцию | `care` |
| `lost_after_first` | 1 визит и > 90 дней | приглашение на осмотр | `care` |
| `sleeping_valuable` | высокий LTV, > 180 дней | приглашение к своему врачу | `care` |
| `child_checkup` | `is_child`, > 180 дней | осмотр ребёнка | `calm` |
| `seasonal` | август (перед школой), май–июнь (перед отпуском) | осмотр перед школой/поездкой | `light` |
- `priority = expected_value × urgency`, где `expected_value` = средний чек предлагаемой категории × оценка вероятности отклика (взять из `triggers.yaml`, подписано как допущение), `urgency` растёт с просрочкой относительно `follow_up_days`.
- Один пациент может иметь несколько триггеров; в интерфейсе показывается топ-1 по приоритету.

### Шаг 2. Признаки из комментариев (часы 8–16)
- Быстро: регулярные выражения → теги `parent` (`мама|ребен|сын|доч`), `pregnant_or_nursing` (`беремен|кормящ`), `anxious` (`тревож|боит|пережива|страх`), `price_sensitive` (`дорого|рассрочк|скидк|подума`), `thinking` (`подумает|думает|решит`), `complex_case` (`презентац|план лечения|имплантац`).
- Лучше: один пакетный проход LLM по непустым комментариям (~7,5 тыс.) с ответом в JSON-список тегов. **В LLM отправлять только текст комментария, без фамилии и имени.** Кэшировать результат.
- Тон по персоне: `anxious` / `parent` / `pregnant_or_nursing` → `calm`; `complex_case` или имплантация/ортопедия → `reliability`; только гигиена, мало визитов → `light`; остальные → `care`.

### Шаг 3. Тексты (часы 14–26)
- Сначала **шаблоны** на каждый триггер × тон (`templates.py`). Демо должно работать без LLM.
- Затем LLM: системный промпт — «заботливый администратор клиники "Ильфа"». Вход: триггер, повод, категории прошлого лечения, давность, тон, канал. Ограничения: до 300 символов для SMS/мессенджера; без давления и капслока; без медицинских обещаний и диагнозов; не упоминать услуги, которых не было в истории; обращение `{name}` как плейсхолдер — имя подставляется кодом после генерации.
- Провайдер: YandexGPT или GigaChat (152-ФЗ), ключ в `.env` (`LLM_API_KEY`), запасной — шаблон.
- Кэшировать тексты в таблице `offers` (`generated_by = 'llm' | 'template'`), не генерировать при каждом открытии.

### Шаг 4. Проверка качества (часы 24–32)
- Вручную оценить 30–50 текстов по чек-листу: повод уместен; тон соответствует персоне; нет выдуманных фактов; нет давления. Результаты — в `offers/QUALITY.md`.
- Автопроверка: в тексте нет услуг вне истории пациента, длина в лимите, есть плейсхолдер имени.
- Метрики для пилота (передать в `docs/`): отклик и запись по каждому триггеру, A/B «шаблон vs LLM».

### Шаг 5. Опционально
- Модель вероятности возврата: признаки RFM + категории; таргет — визит в следующие 90 дней; обучение на первых 9 месяцах, проверка на последних 3. Использовать как множитель в `priority`.
- Next-best-service по матрице переходов от `analytics/`.

### Шаг 6. Материалы для презентации (часы 30–40)
- `EXAMPLES.md`: 3 ярких примера разных персон (родитель, пациент с имплантом, «только гигиена») + ещё 7–12.
- Схема движка: правила → признаки → LLM → проверка → оффер (mermaid).

## Зависимости
- Ждёшь от `etl/` таблицы и справочник услуг; от `analytics/` сегменты и переходы (~16 час). До этого работай на своих правилах.
- Отдаёшь `app/` таблицу `offers` к ~20 часу (формат — контракт).
- Отдаёшь `docs/` примеры и метрики к ~24 часу.

## Критерии готовности
- `python -m offers.build` без LLM заполняет `offers` для всех пациентов с поводом.
- Тексты для разных персон явно различаются по тону.
- В LLM не уходит ни одной фамилии/имени.

## Нельзя
- Менять файлы вне `offers/`. Коммитить ключи и данные. Отправлять персональные данные во внешние API.
