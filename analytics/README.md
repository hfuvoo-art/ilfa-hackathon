# Аналитика «Ильфа»

Сегменты и RFM, исторический и прогнозный LTV, услуги и скидки, переходы, удержание и восемь графиков Plotly. Продолжение ранее подготовленной аналитики; схема — из `shared/DATA_CONTRACT.md`.

## Установка и проверка

Python 3.11+, команды из корня репозитория:

```powershell
python -m pip install -r analytics/requirements.txt
python -m unittest discover -v
python -m analytics.charts
Start-Process .\analytics\charts\demo.html
```

Демо использует только вымышленные данные, создаёт SQLite в памяти и автономный HTML с восемью графиками. Оно не открывает рабочую базу.

Для ноутбука:

```powershell
python -m pip install -r analytics/requirements-notebook.txt
python -m analytics.verify_notebook
```

`analysis.ipynb` открывается в VS Code с ядром Python. В нём есть разведка, сегментация, LTV, услуги, переходы, календарь, удержание и сценарий кампании. `verify_notebook` проверяет формат и выполняет все ячейки в IPython дважды из корня и дважды из `analytics/`, без сетевого ядра. Результаты выполнения в публикуемом ноутбуке очищены.

## Работа с локальной базой ETL

Сначала создайте базу по инструкции `etl/README.md` и сделайте резервную копию. По умолчанию используется `sqlite:///data/ilfa.db`; другой путь задаётся переменной `DATABASE_URL`.

```powershell
python -m analytics.segments
python -m analytics.services
python -m analytics.services --transitions-csv
```

Первая команда записывает **только** `patients.segment`, `rfm`, `ltv_hist`, `ltv_pred` в одной транзакции. Ошибки сверки прерывают операцию; базовые поля ETL не исправляются автоматически. Остальные команды читают базу и печатают отчёты в stdout.

Исторический LTV равен выручке с учётом возвратов, включая отрицательный итог. Прогноз равен неотрицательному среднему чеку × годовой частоте платных повторов по когорте. Для оценки частоты нужно минимум 30 дней наблюдения; для недавних когорт используется общая частота доступных когорт, а при отсутствии оценки — ноль. Прогноз не прошёл проверку на будущем периоде.

## Интерфейсы для команды

```python
from analytics.segments import compute_segments
from analytics.services import build_service_report
from analytics.charts import build_charts

summary = compute_segments(engine)  # запись четырёх полей
report = build_service_report(engine)  # чтение
figures = build_charts(engine, service_report=report)  # чтение
```

Ключи `figures`: `segments`, `pareto`, `ltv`, `services`, `retention`, `transitions`, `monthly`, `weekday`. Каждая фигура содержит пояснение. Графики читают уже рассчитанные сегменты; после обновления ETL сегментацию следует запустить заново. Во время расчёта дашборда используйте согласованный срез базы без параллельной загрузки ETL.

Приоритет сегментов: «Ценные лояльные» → «Новые» → «Незавершённое лечение» → «Пропал после 1 визита» → «Только гигиена» → «Спящие» → «Дети и семьи» → «Активные». Названия соответствуют контракту роли. Признак незавершённого лечения основан на названиях этапов и требует проверки специалистом.

## Материалы и публикация

- `TEAM_SUMMARY.md` — краткие выводы для команды и защиты.
- `FINDINGS.md` — прежние агрегаты клиники, отдельно синтетические результаты и сценарии.
- `HANDOFF.md` — передача владельцам приложения, предложений и презентации.
- `SERVICES.md` — методика услуг и формат матрицы переходов.
- `VALIDATION.md` — что проверено и что нельзя подтвердить без исходной базы.

В Git входят только исходный код, тесты, документация и очищенный ноутбук. SQLite, Excel, CSV, архивы, реальные JSON, сгенерированные HTML и окружения исключены. `.gitignore` не удаляет уже отслеживаемые файлы: перед коммитом проверяйте `git diff --cached --name-only` и содержимое diff. Названия услуг в локальных отчётах могут содержать ФИО врачей; готовые отчёты по рабочей базе не предназначены для публичной публикации.
